# clarifying-requirements

将零散需求材料整理成可评审的《需求规格文档》：先澄清，再对照现有代码，再成文。

产物固定为同一目录下的两个文件：`requirement-spec.md`（规格）与 `requirement-question.md`（澄清记录）。

## 适用场景

适用于：
- 用户给了原始需求文档、问答记录、原型、UI 图，希望产出正式规格文档
- 需求里可能有歧义、自相矛盾、与现有代码/现状不一致的地方
- 需要补出「准入 Case / 验收 Case」

不适用于：
- 直接做技术设计或任务拆解（用 outline-design / detailed-design）
- 只想问某个局部功能怎么实现

## 必需输入

先向用户收集：
1. **需求文档**（必需）
2. **原型链接/文件**（可选）
3. **UI 设计图**（可选）
4. **相关代码范围**（如用户没给，需要自己搜索）
5. **产物输出目录**：确认两个产物文件落在哪里（与「产出规格文档」一步呼应）

如果 UI 图在本地目录里，直接读取图片；不要假设外链文档一定可靠。

如果需求只以**粘贴文本**提供、没有可写目录：先在对话里给出完整草案，并请用户指定落盘位置后再写文件。原因是凭空选一个公共源码目录写产物，容易污染他人代码、也不便回溯。

## 工作原则

1. **先读材料，再写文档**。
2. **必须浏览相关代码**，确认需求是否与当前实现冲突。原因是需求文档常与现状脱节，不看代码就成文会把错误传导到设计和开发。
3. **有歧义先提问**，不要擅自补全业务规则。
4. **区分责任边界**：产品/UI 描述、后端接口行为、下游系统行为不要混写。
5. **准入 Case 优先写「业务可观察结果」**，少写技术实现细节。

## 工作流程

### 第 1 步：收集材料

至少确认：
- 原始需求文档有哪些版本
- 是否有问答澄清记录
- 是否有现成的需求规格样例文档可对齐风格（可选）
- 是否有 UI 图、流程图、接口文档

**必问规则**：如果用户只提供了原始需求文档，**必须询问是否有原型、UI 设计图**。即使用户回复「没有」，也要在 `requirement-question.md` 里记录「未提供原型/UI 图」。这样做是因为缺少原型/UI 时很多交互口径只能靠假设，事后需要可追溯。

如果用户提供了现成的规格样例文档，可提取它的标题层级、章节顺序、Requirement / Acceptance Criteria 表达方式、准入 Case 组织方式、附录/变更点/澄清记录写法。没有样例时，使用本 skill 的通用规格结构。

### 第 2 步：提取事实

从需求材料里提取：背景/目标、名词解释、功能模块、核心业务规则、状态机/条件/例外分支、非功能约束、待确认问题。

把「干扰信息」「历史废弃方案」「外链但已不可信内容」显式剔除。

### 第 3 步：核对现有代码

必须搜索并阅读相关代码，重点找：
- 现有数据模型 / 状态字段
- 现有入口和流程节点
- 当前已存在的约束、校验、枚举、状态机
- 已有接口返回结构
- 哪些能力属于本系统，哪些依赖下游

如果发现以下情况，必须单独列出并询问用户：
- 需求文档和代码冲突
- 不同版本文档互相冲突
- 文档把前端行为写成后端责任
- 文档把系统级回归约束写成单个 case

### 第 4 步：发起针对性提问

**务必发出的询问（不可省略）：**
1. **缺失材料**：只提供原始需求文档时，询问是否有原型、UI 设计图
2. **矛盾点**：需求自身矛盾、和当前代码矛盾的地方
3. **不明确与假设**：需求不明确、需要自己做假设的地方

其他优先问的问题：
- **口径问题**：术语、状态、时间点、渠道定义
- **边界问题**：谁负责弹窗、按钮置灰、通知、补偿

问题要具体，不要泛泛地问「还有什么补充吗」，因为模糊的问题换不回可落地的答复。

**优先使用 AskUserQuestion 发起询问**（若环境无该工具，则直接在对话中提问），拿到用户的选择或文字答复后，再写入 `requirement-question.md`。

`requirement-question.md` 写入规则：
- 与 `requirement-spec.md` 放在同一输出目录
- **每条问题必须在用户答复后才记录**，至少包含：`问题`、`原因/冲突点`、`用户答复`、`对 requirement-spec.md 的影响`
- 即使问题后来已澄清，也保留记录，方便回溯

### 第 5 步：产出规格文档

先确定输出文件位置：
- **优先**：如果原始需求文档所在目录适合放评审产物，直接写到该目录，输出 `requirement-spec.md` 与 `requirement-question.md`
- **否则**：在当前项目内新建一个语义清晰的目录，再写入这两个文件
- 是否「适合」不明确时优先询问用户；若用户未指定，选择最贴近原始需求文档、且不污染公共源码目录的位置

文档建议结构（章节名沿用 EARS/规格惯例，保留英文）：

```md
# Requirements Document

## Introduction
## Alignment with Product Vision
## 术语与口径说明
## Requirements
### Requirement 1: ...
#### Acceptance Criteria
## Non-Functional Requirements
## 准入Case
## Open Questions / Assumptions / Conflicts
## 附录：变更点 / 澄清记录
```

写文档时补齐这些要求：
- **Alignment with Product Vision**：说明需求如何支持产品目标或业务目标
- **User Story**：使用 `As a [role], I want [feature], so that [benefit]` 格式
- **Acceptance Criteria**：优先使用 EARS 风格；按语义正确使用 `WHEN / IF / WHILE / WHERE`
- **Edge Cases and Technical Constraints**：补出关键边界条件、例外流程、技术约束
- **条件触发的 toast / 弹窗文案**：所有由后端根据条件返回、需要前端原样展示的提示文案（toast、错误提示、确认弹窗、阻断弹窗等），必须把**确切文案原文**写入到对应 Requirement 的 Acceptance Criteria 或字段说明块中，不能只写「按情况提示」。原因是这些文案是后端契约的一部分，写模糊了开发和测试无法对齐。前端纯界面静态文案（普通占位符、固定按钮 label）不在此约束内。

### EARS 语义速记
- `WHEN <trigger> THEN 系统 SHALL <response>`：**事件驱动**，某事件发生后系统做出的响应（点击、提交、保存成功、消息到达）
- `WHILE <state> THEN 系统 SHALL <response>`：**状态驱动**，系统处于某持续状态期间始终满足的行为或约束
- `WHERE <feature is included> THEN 系统 SHALL <response>`：**可选功能**，仅在某特性/配置被启用时才适用的行为
- `IF <unexpected condition> THEN 系统 SHALL <response>`：**异常处理**，异常、非法输入、边界条件下的处理
- 普通恒定要求可直接用 `系统 SHALL ...`，不必强行套 `WHEN`

每个 Requirement 建议包含：User Story、Acceptance Criteria、字段说明（枚举/筛选项/表头/详情字段/按钮集合/默认值，如适用）、明确的触发条件/结果/例外条件。

当材料不足、用户暂未回复、或代码与文档冲突时，**仍然输出完整草案**，但必须显式区分：
- **Confirmed**：已被材料、代码或用户答复确认的事实
- **Assumption**：为便于评审暂时采用的假设
- **Open Question**：必须由用户/产品补充确认的问题
- **Conflict**：文档版本之间，或文档与当前代码之间的冲突点

### 第 6 步：每次改动后的复核循环

**每次 `requirement-spec.md` 改动后**（含初次生成和后续修订），必须执行：
1. 重新比对 `requirement-spec.md` 与原始需求文档
2. 重新比对 `requirement-spec.md` 与 `requirement-question.md` 已记录的问题和答复
3. 检查是否有新产生的矛盾、遗漏或未覆盖的需求
4. 如果有新问题，追加到 `requirement-question.md` 并向用户发起询问

循环持续到 `requirement-spec.md` 与原始需求和问题列表完全对齐为止。

## 准入 Case 规则

写准入 Case 时，快速检查：
1. 它验证的是**用户/业务可观察结果**，不是实现细节
2. 它验证的是**本次需求本身**，不是顺带验证别的系统
3. 它不是过大的系统级回归约束

优先保留：正常流程、关键异常流程、状态流转、配置变更/快照类边界场景。

谨慎写入：「写库成功」「发 MQ 成功」这类底层细节；无法从接口或业务视角直接观察的副作用；明显属于联调/集成测试的并发、幂等、时序问题。

## 产出质量标准

最终文档应做到：
- 能直接给产品、研发、QA 评审
- 术语口径一致
- 每条规则都能追溯到材料或用户澄清
- 明确列出未决问题
- 最终结果不是只在对话里展示，而是**落成文件 `requirement-spec.md`**

## 范例

> 以下范例使用中性场景「提交工单 → 审批 → 满足条件发通知」，仅示意写法，不绑定任何具体业务。

### 范例 1：Requirement 写法

```md
### Requirement 1: 工单提交与状态模型

**User Story:** As a 普通用户, I want 提交工单并跟踪其状态, so that 能在审批完成前后清楚地知道处理进展。

#### Acceptance Criteria
1. WHEN 用户提交合法工单 THEN 系统 SHALL 记录提交人 UID、工单类型、提交时间，并将状态初始化为「待审批」
2. IF 同一用户存在未结束的同类型工单 THEN 系统 SHALL 拒绝创建并返回「已有处理中的同类型工单」
3. WHILE 工单处于「待审批」状态 THEN 系统 SHALL 允许提交人撤回该工单
```

要点：标题写业务能力不写实现方案；User Story 保留角色/目标/收益；按 EARS 语义正确区分 `WHEN / IF / WHILE`；每条只表达一个明确规则；枚举/字段不要塞进 EARS。

### 范例 2：准入 Case 写法

```md
#### F0-01 提交工单——无在途工单，提交成功
**覆盖需求**：Req 1 工单提交

**前置条件**
- 用户当前无未结束的同类型工单

**步骤**
1. 进入「提交工单」页
2. 选择工单类型，填写内容
3. 点击「提交」

**预期结果**
- 提交成功，页面刷新为「待审批」状态
- 列表中出现该工单
```

要点：准入 Case 写「前置条件 / 步骤 / 预期结果」三段；预期结果写业务可观察现象，不写 DB/MQ 细节；用例名体现入口、场景、结果。

### 范例 3：边界 Case 写法

```md
#### F0-09 审批通知——同一工单重复审批仅通知一次
**覆盖需求**：Req 3 审批与通知

**前置条件**
- 工单处于「待审批」
- 通知渠道可用

**步骤**
1. 审批人提交「通过」
2. 观察通知发送结果
3. 因重试再次收到同一审批结果
4. 再次观察通知发送结果

**预期结果**
- 第一次审批后状态流转为「已通过」，发送一次通过通知
- 重复审批不再重复发送通知
```

要点：边界 Case 优先挑「幂等 / 状态流转 / 配置快照」这类真正容易出错的业务规则，不要把纯技术实现细节写成 Case。

## 常见错误

- 没看代码就直接重写需求
- 把 UI 原型文案原封不动抄成后端规则
- 把「使用建议 / 运营话术 / 操作习惯」写成系统功能需求（例如「优先引导用户做某动作」），而不是写成系统可观察能力或入口约束
- 把枚举值、列表筛选项、表头字段这类字段口径说明写进 EARS 功能描述，而不是拆到单独的字段说明块
- 把技术实现细节写成准入 Case
- 发现冲突不提问，直接脑补
- 忽略「当前系统已实现什么、缺什么」这层事实校验
- `requirement-spec.md` 改动后不再做二次复核

### 反例：把使用方法写成系统需求

坏写法：
```md
WHEN 用户可提交工单 THEN 前台 SHALL 优先引导用户走在线提交，而不是线下登记
```

问题：这是人员操作建议，不是系统行为，无法从系统侧稳定验收「是否优先引导」。

好写法：
```md
WHEN 用户进入工单入口 THEN 系统 SHALL 提供在线提交入口与必要的类型选择能力
IF 系统中找不到对应可提交的工单类型 THEN 前台页面 SHALL 不提供线下补录入口
```

要点：写系统可观察能力或入口约束，不写培训话术、岗位 SOP 或人员偏好。

### 反例：把字段/枚举口径写成 EARS 功能描述

坏写法：
```md
WHEN 展示工单状态 THEN 系统 SHALL 统一使用 待审批 / 已通过 / 已驳回 / 已撤回 四种状态口径
WHEN 查询工单 THEN 系统 SHALL 支持按 工单号 / 提交人 / 类型 检索
```

问题：这是字段口径/查询项说明，不是「功能触发后的系统行为」，混进 EARS 会降低可读性。

好写法：
```md
#### Acceptance Criteria
WHEN 审批人提交通过 THEN 系统 SHALL 将工单状态流转为 已通过

#### 字段说明
- 状态枚举：待审批 / 已通过 / 已驳回 / 已撤回
- 列表查询支持的筛选项：工单号 / 提交人 / 类型
```

要点：EARS 只写功能行为、状态流转、约束结果；枚举、筛选项、表头、详情字段单独放到字段说明块。

### 反例：混用 WHEN / IF / WHILE 语义

坏写法：
```md
WHEN 工单处于待审批状态 THEN 系统 SHALL 隐藏删除按钮
WHEN 用户无提交权限 THEN 系统 SHALL 阻断提交
```

问题：`待审批状态` 是持续状态应用 `WHILE`；`无提交权限` 是条件分支应用 `IF`。

好写法：
```md
WHILE 工单处于待审批状态 THEN 系统 SHALL 隐藏删除按钮
IF 用户无提交权限 THEN 系统 SHALL 阻断提交并返回无权限提示
```
