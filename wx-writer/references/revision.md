# 公众号改稿检查

初稿完成后，先调用 `human-writing` 做通用语言、材料和事实检查，再按本文件检查公众号文章的结构与个人风格。不要在这里复制上游技能的禁词表。

审阅遵循主文件的“审稿权限”：先出问题和局部建议，`wx-writer` 保留初稿并落实授权范围内的修改。不要把上游的删改要求直接变成覆盖全文的操作。有具体内容和幽默反差的并列按 `voice.md` 中已确认例外处理。最后对照初稿检查幽默、判断、结构和硬资产是否被误删或改弱。

## 结构

- 开头是否从具体的人、事、场景、反差或结果进入
- 核心问题是否在前几段变得清楚
- 每个板块是否推进了新的事实、机制、区别或后果
- 标题层级是否服务于阅读，是否有为了凑结构而切碎的短板块
- 原文的表格、数据、截图、流程图、代码、图片和列表是否保留
- 结尾是否停在具体事实、人物动作或当前判断上

## 个人风格

- 作者是否像一个做过实际研发的人
- 专业信息是否是正文的主体
- 开头、转折或结尾的幽默是否自然，是否没有强行插入
- 生活化表达是否帮助理解，而不是把文章写成网络口播
- 判断是否绑定了事实、机制、代价或结果
- 是否分析了谁获得了什么、谁承担了什么成本
- 是否出现模仿某个作者的人设、口头禅或标题套路

## 传播性

- 标题是否具体，是否说清楚问题、冲突或代价
- 开头是否让读者知道为什么现在要读这篇文章
- 是否有一两个值得转发的判断。没有就不凑
- 是否有一段只有正确废话，删掉后文章是否更紧
- 传播性来自事实和判断，还是只来自语气和标题

## 金句候选

金句不是硬指标。只有一句话脱离上下文仍然成立，并且准确承载了本文的重要判断时，才列为候选，最多两句。

候选句应说明：

- 它对应的事实或判断是什么
- 为什么脱离上下文仍有价值
- 是否适合在 HTML 中做轻量视觉强调

没有合适候选时不标，也不添加“本篇不标金句”的流程说明。

## 局部优化

用户询问某段如何优化时：

1. 先指出该段的具体问题
2. 通常给两个只针对该段的改法，最多三个，不凑选项
3. 说明每个改法会改变什么
4. 等用户选择后再动笔

不得借局部调整切换整篇文章的人格或默认语气。

用户已明确指定改法时直接执行，不重复征求选择。
