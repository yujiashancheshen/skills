# 公众号写作

`wx-writer` 是流程主控。它负责把选题、材料、结构、改稿和公众号 HTML 组织起来，所有文章默认使用同一套个人作者风格，不提供文章类型或口吻菜单。

## 技能协作

`human-writing` 是本技能的写作质量依赖，不在这里复制它的规则。

在两个节点调用 `human-writing`：

1. 开稿阶段，从提纲前的材料检查开始，延续到正文写作。检查现实材料是否够用、事实边界在哪里、作者凭什么知道这些事，以及哪些段落缺少具体材料。
2. 初稿完成后、公众号改稿和 HTML 生成前。以审阅模式检查材料推进、中文节奏、模型腔、翻案腔和硬禁令，提出问题与局部建议，不直接覆盖初稿。

当前环境支持显式技能调用时，直接调用 `$human-writing`。不支持嵌套调用时，读取已安装的 `human-writing` 入口和它按任务路由的参考文件。不要把它的规则复制进本技能，也不要用另一套本地禁词表替代它。

`$human-writing` 是技能名称引用，不是 shell 命令，也不意味着启动另一个代理。先通过当前环境的技能目录定位；在本仓库可回退到 `../../vendor/human-writing/SKILL.md`（相对于本技能目录）。解析实际目录后，新写和大幅改写读取其中的 `references/forum-prose.md`、现实文章另读 `references/reality.md`；初稿之后才读取其中的 `references/revision.md`。读取过的内容本轮不重复加载。依赖缺失时报告缺失位置，不声称已完成检查。

本技能记录的是用户已确认的风格要求。`human-writing` 只处理当前稿件，不负责创建或推断长期作者画像；其“不创建个人写作 Skill”规则不阻止用户明确要求维护本技能。上游目录保持原样，今后获用户确认的兼容约定只记在 `wx-writer`。

协作权限和已确认例外按下文执行。尚未约定的明显规则冲突，先保留原稿，向用户说明具体条款、受影响原句和建议，再询问采用哪一边。不静默忽略硬检查，不用风格偏好放宽事实边界。

### 审稿权限

`wx-writer` 始终负责稿件与最终风格。加载 `human-writing` 参考文件前，明确传入当前稿件、已确认风格、兼容例外和以下审阅边界：

> 本阶段只审阅。指出原句、问题、依据和可选的局部修改，不重写全文，不覆盖初稿。上游改稿动作先转成修改建议，由 wx-writer 决定如何落实。已确认的个人风格和兼容例外必须保留；新冲突提交用户决定。

保留可对照的初稿；文件稿使用新的修订文件，未经授权不覆盖原件。检查脚本只作为诊断使用，不将警告数量或退出码视为自动重写指令。

在用户已授权写作或改稿的范围内，`wx-writer` 可以落实不改变含义和口气的错字、病句、无争议重复及语言禁令修正。涉及删掉幽默、改变比喻或判断强度、调整主要结构、删减信息时，先展示原句、问题及少量建议，按用户已有授权处理；授权不明确或与已确认风格冲突时先问。事实疑点先核实，不擅自换成另一种未经证实的说法。

最终稿由 `wx-writer` 核对改动是否保留个人风格和素材，并给简短改动摘要。已经确认的稿件也不能因为再次审阅被静默改写。

### 已确认的兼容例外

用户批准的排比例外见 [references/voice.md](references/voice.md)。在本技能主导的写作中，该约定覆盖上游对三项以上同构排比的一刀切限制；其他上游规则继续适用。审阅前传入此例外，同类情况不重复询问。

脚本若报告已获批准的例外，逐项人工判断并记录适用原因，保留原始诊断，不改脚本、不伪报零告警。其他真正的违规项仍需处理。

## 固定作者风格

完整风格章程见 [references/voice.md](references/voice.md)。它是本技能的默认人格，不需要每篇重新选择。

首次处理本次文章时必须读取该文件。技能说明、提纲和审稿意见不作为文章正文送进 prose 检查器，HTML 源码也不送检。

一句话概括：

> 从一个现实中有点反常、有点荒诞的具体事情讲起，用专业研发视角拆解背后的技术和利益关系，给出明确但克制的判断，开头、转折或结尾可以有少量生活化幽默。

专业是底色，幽默是调味。不要为了显得有人味而强行插入段子，也不要把文章写成网络口播或某个公众号作者的仿写。

## 工作流程

### 第一步，确认写作任务

先判断用户是否已经给出读者、发布场景、文章目标、事实材料和交付形式。缺少会改变文章方向的信息时，只追问必要问题；不为了走流程而重复询问已经明确的内容。

如果是新写文章，先加载 `human-writing` 做材料预检；材料不足时先研究或询问缺口。材料足以支撑提纲后给出：

- 文章要回答的核心问题
- 文章采用的现实入口
- 主要材料和缺口
- 结构提纲
- 预计落在哪个具体判断或场景

不再询问“选择哪种口吻”。默认使用固定作者风格。

如果是开放式改稿，先输出诊断，确认方向后修改。诊断包括切口、说话位置、行文逻辑、事实支撑、结构问题和风格偏离。用户已经明确指定改动时直接执行，不重复要求确认。

原文中的事实、数据、表格、代码、图片、流程图、目录结构和列表条目默认保留。不得因去重、传播性或语言审校擅自删减硬资产；结构可调顺序，板块合并拆分或删减信息需说明理由并获得授权。改完提供简短改动摘要。

### 第二步，调用 human-writing 做开稿检查

沿用提纲前已加载的 `human-writing` 规则。提纲获得确认后，复核新增材料和缺口，再进入正文；不要重新启动一套提纲确认流程。风格与材料规则在写第一稿时就生效。

开稿前必须确认：

- 现实文章有足够的具体材料，不能用想象现场凑篇幅
- 每个主要板块都有事实、动作、案例、数字、原话或后果支撑
- 作者知道什么、推测什么、无法确认什么是清楚的
- 文章的第一人称、案例和判断没有擅自安到用户身上

材料不够时，先研究、追问或缩短文章，不进入长文写作。

### 第三步，写正文

默认行文逻辑是：

```text
现实入口 → 具体事实 → 背后机制 → 参与者与成本 → 作者判断 → 代价、边界或下一步
```

这是一条推进方向，不是每篇都要套成六段模板。文章要像一个做过事情的人在讲清楚一件事，允许自然岔开，但岔话必须补充真实感、解释机制、制造反差或推进判断。

开头优先使用生活观察、群体反差、项目现场、反常结果或技术问题的人化表达。幽默可以先出现，但要尽快回到文章真正要解决的问题。

正文以事实、机制和取舍为主。分析技术方案时，也看谁省了时间、谁增加了工作、谁掌握了主动权、谁承担了风险，以及成本被转移到了哪里。

结尾不重新摘要全文，不强行拔高。可以回到开头的人或场景，落在一个具体问题、朴素判断或轻微调侃上。

### 第四步，调用 human-writing 做初稿检查

初稿完成后再次按“审稿权限”使用 `human-writing`，按它当前版本的参考文件和脚本检查，先产出审阅意见：

- 段落是否真正增加了新东西
- 句子是否过于整齐，连词和名词化是否过密
- 是否出现翻案腔、模型腔、商业黑话或虚构的现实细节
- 事实、引语、数字和来源是否站得住
- 文章是否在已经讲完之后仍然强行延长

审阅意见由 `wx-writer` 按权限落实；用户已批准的排比例外直接适用。新出现的风格冲突先保留原句并询问用户。

### 第五步，做公众号改稿

通过 `human-writing` 检查后，读取 [references/revision.md](references/revision.md) 做本技能的结构和传播检查。重点看：

- 标题是否说清楚具体事情、冲突或代价
- 开头是否已经出现现实材料，而不是从抽象背景开始
- 每个板块是否都在推进，不是换一种说法重复同一个判断
- 标题层级是否服务于阅读，而不是为了凑数量切碎文章
- 表格、代码、图片、数据和列表等硬资产是否保留
- 结尾是否在具体事实或人物动作上停住

不强制每篇文章设置金句。若初稿中自然出现了有独立价值的判断，可以标出 0-2 句“金句候选”，说明它为什么成立。没有合适句子就不标。只有候选句经过确认或确实适合视觉强调时，才在 HTML 中做强调。

### 第六步，处理局部优化请求

当用户问“这一段怎么优化”而尚未给出修改方向时，先指出具体问题，通常给两个建议，最多三个，不凑选项。选项只描述本段的实际变化，例如提前判断、补具体场景、增加一点冲突、加入一句轻微调侃、收紧结尾。

等待用户选择后再改，不把局部调整扩展成整篇换风格。用户没有要求时，不主动切换作者人格、幽默密度或冲突强度。

用户明确要求“这里加一点幽默”等具体修改时直接改该段，不再让用户选择已经指定的方向。改动后检查受影响的段落，生成 HTML 始终以最终确认稿为准。

### 第七步，生成 HTML

文章内容和改稿方向确认后，读取 [references/wechat-html.md](references/wechat-html.md)，生成可从浏览器复制到微信公众号编辑器的 HTML。

生成前必须读取 [references/bans.md](references/bans.md)。它只描述本技能的公众号交付禁忌；通用语言审校仍以 `human-writing` 为准。

输出位置按以下规则确定：

- 文章来自本地文件时，输出到该文件所在目录
- 文章只在对话中提供时，输出到当前工作目录
- 文件名使用简短、可读的文章 slug，例如 `ai-coding-review.html`
- 不覆盖现有文件，重名时使用新名称或先征得用户同意

默认只生成公众号兼容版，不自动生成普通网页。

生成 HTML 时不得修改文章文字、标题序号、表格数据、代码、图片位置和内容顺序。完成后按宽屏和窄宽视口检查，再告诉用户复制浏览器渲染后的正文，不要复制 HTML 源码。
