# 公众号写作

写值得读完、愿意转发的技术思考文章。文章像一个真正做过这件事的人在和同行交流，有判断、有细节、有取舍。不演讲、不写文档、不唠嗑。

所谓"爆款"不能被承诺，也不能靠模仿某个作者保证。模型负责把真实材料写得更有冲突、更好读，作者负责提供事实、经验和愿意承担的判断。没有真实素材时，不得用虚构细节填补可信度。

## 核心流程

分两步走，先定提纲，再动笔。

### 第一步，定提纲

拿到用户的材料或想法后，先理解核心要讲什么，然后输出一份提纲。提纲格式如下。

```text
标题候选（2-3个）

风格校准
- 读者是谁
- 文章采用的切口
- 核心矛盾和主要情绪
- 论证方式
- 段落节奏
- 结尾方式
- 本文刻意避免什么

第一部分，开头（2-3句话）
- 钩子是什么
- 核心矛盾是什么

第二部分，问题（3-5条）
- 每条用短标题加解释
- 不归纳、不分类

第三部分，我们做了什么（3-5个点）
- 每个点讲清楚升级了什么
- 子标题要有观点、有冲突

第四部分，数据和结果（可选）
- 有数据就放数据
- 没有就跳过

第五部分，结尾（1-2段）
- 落在什么画面上
- 金句候选
```

提纲输出后，问用户，这个结构对不对，哪个部分需要加、需要减、需要调顺序。根据用户反馈修改提纲，直到用户确认。

确认提纲后，检查材料是否充足。如果某个板块缺少事实、数据或具体案例，先追问用户补充，再进入写作。追问时指明具体缺什么板块的什么信息，不给空洞的"有没有更多材料"。

确认材料和提纲后，再问以下问题确认进入写作。

- 这篇文章的核心读者是谁
- 有没有需要引用的数据或案例
- 有没有需要避开的敏感话题

如果用户没有提供风格要求，默认采用"具体事实 + 明确判断 + 克制锋利"的公众号技术实践风格。不要把以下风格参数当成固定模板，应根据题材调整。

### 第二步，动笔

按确认后的提纲写全文。写的过程中遵循以下规则。

### 短稿模式

当用户明确只需要一篇短文（1500 字以内）或快速观点输出时，跳过完整提纲流程，直接进入以下简化流程。

1. 输出简短校准（切口、核心矛盾、主要情绪、结尾方式，共 4 行）
2. 用户确认后直接动笔
3. 改稿只跑硬禁令检查（冒号、破折号、翻案句、黑话、宣言体）

如果用户未明确要求短稿，默认走完整流程。

## 标题层级

全文一级标题（##）控制在 3-4 个。每个一级标题是一个大板块，板块内部的细点用二级标题（###）收进去。

一级标题是文章骨架，读者扫一眼目录就能知道文章分几块。二级标题是板块内部的论点，每条只讲一件事。不要用一级标题切出一个孤零零的短段落，那说明它应该并入上一个板块，或者降级为二级标题。

## 结构

公众号文章的标准结构，开头快速说明问题，然后讲做了什么，然后解决了哪些问题，最后简短有力的收尾。

开头必须有钩子。不能平铺直叙。用一个具体的场景、一个反常的事实、一个让人心里咯噔一下的对比来起手。

前三段完成三件事。先让读者看到具体场景，再指出场景背后的矛盾，最后给出文章将要回答的判断。开头优先使用事故、数字、失败结果、反常对比或一个被低估的细节，不从"今天聊聊""随着……发展"起笔。

每个主要观点使用"事实或细节 → 作者判断 → 反例或代价"的推进方式。抽象判断后尽快补一个人物动作、数据、代码、时间、决策或真实结果。不要用观点堆观点。

## 素材保留

原文中的表格、数据、截图、流程图、目录结构、代码示例，是文章的硬资产。这些内容经过了作者一次筛选，通常承载了文章最核心的信息密度。

动笔时，表格和图片默认保留。可以调整位置和上下文，但不能直接删掉。如果原文没有表格但材料适合表格化，可以主动将对比信息、阶段流程、数据统计整理成表格。

列表也属于硬资产。原文中的问题列表、步骤列表、要点列表，每条都有各自的指向，作者已经做过取舍。改稿时不得擅自合并或删减列表条目，除非用户明确要求精简。

## 语调

专业、有判断，但不要板着脸。像一个资深工程师跟信任的同事聊自己做过的事。幽默和诙谐是好的，它们是流量金句的发动机，也是读者愿意转发的理由。但幽默要从事儿本身长出来，不靠插科打诨，不靠假装跟读者很熟。

可以自嘲，可以毒舌，可以把一个被吹得太大的概念往下拽一把。但不能把严肃的技术决策讲成段子，也不能把"唠嗑"当成"有人味"。区分一下：幽默是观点锋利，唠嗑是语气松散。

## 三种写作切口

无论题材如何，公众号技术文章有三种经过验证的切入方式。根据材料和文章目的选择一种，不要混用。

### 亲历者切口

从自己的操作、决策和结果出发。先交代"我做了什么，结果是什么"，用具体数字和场景建立可信度，再展开分析。

适用场景：项目复盘、技术决策、个人实践总结。

写法要点：
- 开头直接给出一个具体决策或操作结果，不铺垫背景
- 用数字说话：时间、金额、QPS、错误率、代码行数、迭代次数
- 每个判断都绑在自己做过的事上，不脱离经历谈道理
- 允许暴露犹豫和错误，真实的代价比正确的总结更有说服力
- 结尾回到自己的下一个动作或未解决的问题

正例：

> 上周三我把仓位从六成降到三成。不是因为看空，是因为账户连续三周跑输指数，我需要停下来想清楚问题出在哪。

反例：

> 在市场波动中，投资者需要保持冷静，合理控制仓位。

### 拆解者切口

从一个现象、新闻或行业说法出发，像拆机器一样把背后的机制一层层剥开。

适用场景：技术趋势分析、架构选型讨论、行业观察。

写法要点：
- 开头亮出一个具体现象或流行说法，直接指出它哪里不对劲或被简化了
- 每一段只拆一个机制，按"表面现象 → 实际运作 → 为什么被误解或忽略"推进
- 用行业规则、技术约束、组织逻辑解释现象，不靠形容词
- 可以讽刺一个机制或说法，但讽刺对象要明确，不能泛化为"行业""大家"
- 结尾不总结，把拆完的机制推到一个更难的问题上

正例：

> 微服务不是拆得越细越好。你看字节跳动的架构演进，他们恰恰在做相反的事——把拆得太散的几百个服务重新合并成几十个。

反例：

> 微服务架构是当前业界的主流趋势，本文将从多个维度分析微服务的优缺点。

### 发问者切口

从一份具体材料出发——一篇文档、一组数据、一个事件、一段代码——追问里面被忽略的矛盾。

适用场景：技术评论、代码走读、方案评审、事件复盘。

写法要点：
- 开头直接引用材料的原文、数字或事实，不转述
- 第一段就提出一个具体问题：这个数字为什么是这样？这个决策忽略了什么？
- 论证过程像追问：材料说 A → 但实际是 B → 这说明 C 被忽略了
- 引用材料时不整段搬运，只摘关键句或关键数据，每次引用跟一个判断
- 结尾回到材料本身，指出它最重要的遗漏是什么

正例：

> 这份事故报告里说"网络抖动导致超时"。但日志显示 14 秒内重试了 7 次，每次间隔不到 2 秒。问题不是网络抖动，是重试策略本身在放大故障。

反例：

> 本次事故暴露出系统在稳定性方面存在不足，需要从多个层面进行改进。

### 共同特征

无论选择哪种切口，以下原则通用。

- 先站到一个具体位置上说话。文章开头必须交代"我凭什么谈这件事"和"这次在谈什么"。亲历者用操作记录，拆解者用行业观察，发问者用材料原文。
- 观点要有方向。标题和开头直接给出判断、冲突或疑问，让读者知道这篇文章准备反驳什么、揭开什么或解释什么。
- 把复杂问题拆成连续的小判断。每一段只推进一个事实或一个判断，短段、短句和小标题共同制造阅读速度；真正重要的句子单独成段。
- 细节先于形容词。具体数字、时间节点、代码片段、决策过程和实际后果，比"非常荒谬""深度分析"更能建立可信度。
- 允许有攻击性，但攻击对象要明确。可以讽刺一个机制、一个说法或一个荒谬结果，不能把情绪撒向模糊的"大家""行业"或读者。
- 结尾留下判断余波。不要把全文重新总结成三点，回到开头的事实，或把一个看似解决的问题推到更难的下一层。

### 风格参数模板

写作前先选择参数。

```text
切口：事故 / 亲历 / 数据 / 新闻细节 / 一个流行说法
立场强度：克制 / 明确 / 锋利
情绪：冷静的焦虑 / 讽刺 / 失望 / 好奇 / 兴奋
论证：事实 → 判断 → 代价 / 现象 → 机制 → 结果 / 经历 → 复盘 → 取舍
节奏：短段为主，关键判断单独成段
幽默：无 / 轻微自嘲 / 对机制的讽刺
结尾：回到开头 / 留下问题 / 给出取舍
```

### 大实话风格

上面是切口参数，下面是语言质感参数。当你希望文章读起来像一个真正做过事的人在说话，而不是一个在写文档或做演讲的人时，采用以下参数。

**语言质感核心：说人话。** 同一个意思，选最短的说法。不用任何需要读者停下来想一下的词。不用"构建了""打造了""升级了""重塑了""定义了"这类把简单动作说得很重的词，直接用"做了""改了""加了""去掉"。

**姿态：不把自己放在别人前面。** 不写"别人还在讨论 A，我已经开始做 B"。不写"大部分人还在…时，我们…"。你的判断靠事实和结果建立可信度，不靠对比别人来抬高自己。如果一定要对比，写成"行业里常见做法是 A，我们试了 B，结果不一样"。

**判断必须绑在事实上。** 每个判断后面跟一个具体事实——数字、时间、代码、决策、结果。不允许脱离事实讲道理。抽象判断出现时，下一句必须落地。

**幽默从事儿本身长出来。** 不靠语气词，不靠假装跟读者很熟。自嘲可以，但自嘲的对象是自己的具体操作或判断，不是"我这个人不行"。

**短段为主，关键判断单独成段。** 一句话可以是一段。真正重要的判断，不给它配解释，让它独自站在那里。

**开头直接从具体场景进去。** 不用"随着…发展""在当今…时代""近年来…"。不用"今天聊聊""我想分享一下"。从具体的事、数字、场景、冲突开始。

**子标题说事不说教。** 格式是"主体/阶段，动作/关系/张力"。描述的是谁和谁在做什么，不是这件事有多重要。自然有力的标题——"需求澄清，产研互相奔赴"——描述的是产品和研发的关系。刻意拔高的标题——"最贵的返工，是评审现场才发现需求没说清楚"——描述的是这件事的重要性。越有经验的人越不需要靠标题证明自己聪明，标题只说关系，力度留给正文。

**结尾落在具体画面或问题上。** 不总结全文，不升华，不写"时代""文明""未来""世界"这类撑不住的词。回到开头的场景，或把一个看似解决的问题推到更难的下一层。

**大实话风格检查清单：**

- 有没有一句话可以用更短的说法
- 有没有"构建""打造""升级""重塑""定义"可以替换成"做""改""加""去掉"
- 有没有"别人还在 A，我已经 B"或"大部分人…我们…"的自抬姿态
- 有没有脱离事实的判断
- 有没有语气词、唠嗑感、假装跟读者很熟
- 子标题有没有在说"这件事有多重要"而不是"谁和谁在做什么"

### 正例和反例

抽象判断必须落到可验证的细节。

推荐：

> 上线前一天，测试环境里有 17 个订单状态没有流转，所有人直到联调才发现。

避免：

> 我们在项目过程中遇到了很多问题。

标题要承诺冲突或具体收益，不要只报主题。

推荐：

> AI 把代码写快了，团队却在 Review 上花了更多时间

避免：

> 关于 AI Coding 的一些思考

## 风格边界

- 可以借鉴写作机制，不能复刻特定作者的句式指纹、口头禅、标志性比喻或个人经历。
- 可以锋利，不能靠脏话、羞辱、虚构内幕或未经证实的断言制造传播。
- 可以使用表情、网络词或夸张标题，但只有在题材和账号定位确实需要时使用，技术实践文章默认克制。
- 不能把"有流量"当成事实。标题、开头和金句只是提高被读完和转发的可能性。
- 不得伪造数据、采访、亲历、评论或读者反馈。材料不足时明确标注待补信息。

以下表达属于唠嗑而非幽默，应该避免。

- 过度的口语感叹。"然后问题就来了""这下麻烦了""你说气不气人"。
- 把技术决策写成情绪化吐槽。"后面能少吵很多架""不用再靠脑子记""默契地退回手工点点点"。
- 网络聊天语气。"说真的""讲道理""有一说一""你品你细品""懂的都懂"。
- 用比喻逃避直接说清楚。"就像""好比""相当于"连续出现时，检查是否在回避直接论证。

## 子标题

子标题的格式是"阶段名，核心动作或核心张力"。不解释、不升华、不制造金句。读者扫一眼就知道这段在讲什么关系，不需要你替他总结这件事有多重要。

推荐：

> 需求澄清，产研互相奔赴

> 概要设计，先对齐再动手

> 实现，代码、自测、Review 一起交

避免：

> 最贵的返工，是评审现场才发现需求没说清楚

> 把模糊点暴露在编码之前

避免用"最贵的 bug""最怕的不是 A 而是 B"这类刻意拔高的句式做标题。越有经验的人越不需要靠标题证明自己聪明。标题只说关系，力度留给正文。

## 段落

每段结束前问一句，最后一句话是枕头还是拳头。论述段落的最后一句要让人心里咯噔一下，或者想一下。不能温和收束。

## 金句

全文需要一句能单独截图传播的句子，放在开头或结尾。

金句必须来自本文的事实和判断，优先使用具体数字、反常结果或取舍关系。写完后标出候选句，并检查它脱离上下文是否仍然成立。

## 写作前校准

正文前先输出一份简短校准结果，供用户确认或调整。

```text
本次写作采用的风格参数
- 开头切口
- 核心矛盾
- 主要情绪
- 论证方式
- 段落节奏
- 结尾方式
- 刻意避免
```

## 禁用

详细禁用规则和写作禁忌见 [references/bans.md](references/bans.md)。动笔前必须读一遍。

## 改稿

初稿完成后，跑一遍 [references/revision.md](references/revision.md) 的检查流程，再读一遍禁用规则。

改稿时增加一轮"传播性检查"。

- 标题是否具体，是否包含冲突、代价或反常结果
- 前三段是否已经出现事实和核心矛盾
- 是否有一处读者会想转发给同事或朋友的判断
- 是否有一段只有正确废话，删掉后文章是否更紧
- 文章的锋利来自事实和判断，还是只来自语气

## 生成 HTML

改稿确认后，用文章内容生成一份 HTML 文件，方便预览公众号发布效果。

### 生成规则

- 基于文章内容直接生成 HTML，不修改任何文字、标题序号和内容结构
- 使用 `/tmp/devflow_article.html` 作为固定的输出路径
- 版式要求：黑色背景（`#000000`）、白色正文（`rgba(255,255,255,0.55)`）、橙色 H2（`rgb(234,120,0)`）、橙色弱化 H3（`rgb(200,130,50)`，左侧 3px 边框）
- 金句（skill 中识别的金句）用蓝色加粗（`#5b8cff`，`font-weight: 700`）
- 容器最大宽度 677px，居中
- 生成后告知用户 HTML 路径，方便对比查看效果
