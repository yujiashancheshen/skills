# outline-design

## 概述

生成中文 markdown 概要设计文档，默认产物 `design-outline.md`。面向前后端联合设计（前端 Vue、后端 Go 多模块），强调固定章节、统一分类规则和概要层级，**不展开到详细设计**（详细设计交给 detailed-design）。

## 适用场景

- 需要在编码前输出概要设计文档时
- 已有 `requirement-spec.md`、PRD、UI 设计稿、原型 HTML、代码仓库中的任意一种或多种材料时
- 需要把前端页面、后端模块、接口、MQ 信息整理成统一文档时

## 固定输出结构

必须固定输出以下一级、二级标题；若某节不适用，内容区只写 `无`。固定章节的作用是约束内容边界，避免概要设计不自觉地写成详细设计。

- `一 可行性分析`
  - `1.1 重点流程`
  - `1.2 状态机`
- `二 前端方案`
  - `2.1 页面变更`
  - `2.2 页面详情`
- `三 后端方案`
  - `3.1 ER图`
  - `3.2 模块变更详细说明`
  - `3.3 接口概览`
- `四 接口文档`
  - `4.1 前后端HTTP接口`
  - `4.2 后端RPC接口`
  - `4.3 后端MQ异步消息`

## 启动检查清单

开始设计前，`AskUserQuestion` 的使用顺序：

1. **必问**：确认输入信息与输出方式
2. **按需提问**：若前端页面归属存在不确定性，再确认页面放在哪个前端模块
3. **按需提问**：若后端表结构/领域归属存在不确定性，再确认表结构变更放在哪个后端模块
4. 完成概要设计；若仍有待确认问题，先输出 `xx-question.md`，待用户补充后继续

### 1. 输入信息与输出方式确认（必问）

确认当前已有的输入材料，以及输出文件的生成方式。

输入推荐选项：
- `需求规格文档（Recommended）` — 如 `requirement-spec.md`
- `需求原始材料` — PRD、需求描述、问答记录
- `设计材料` — UI 设计稿、原型 HTML、截图
- `代码仓库` — 当前目录代码、接口定义、现有实现

输出方式推荐选项：
- `新建 design-outline.md（Recommended）` — 默认在需求规格文档所在目录新建
- `更新已有 design-outline.md` — 在已有文档基础上覆盖或补全
- `指定其它路径` — 由用户明确给出输出路径
- `允许先产出问题清单` — 信息不足时先生成 `xx-question.md` 等待回答

### 2. 前端页面归属确认（按需）

仅当页面归属存在歧义时再问。重点确认有哪些页面、分别在哪个前端模块。

### 3. 后端表结构/领域归属确认（按需）

仅当后端表结构或领域归属存在歧义时再问。重点确认领域层/表结构变更分别在哪个后端模块。

## 取材优先级

按以下顺序综合取材：
1. 用户显式提供的路径、URL、文档
2. 需求规格文档（如 `requirement-spec.md`）
3. 需求原始文档（PRD、UI 设计稿、原型 HTML）
4. 当前目录代码
5. API 平台 / 接口资料（如有必要再主动查询）

有啥用啥，不要求输入齐全。

## 分类规则

### 接口分类规则

固定使用以下规则（通用约定）：
- `/<模块名>/api/` 前缀：归类为 `4.2 后端RPC接口`
- `/<模块名>/mis/` 前缀：归类为 `4.1 前后端HTTP接口`
- `/<模块名>/public/` 前缀：归类为 `4.1 前后端HTTP接口`

绝大部分项目遵循该规则；若发现个别例外，可按实际情况归类，但不要轻易猜测。

**未匹配上述前缀时的兜底**：能被前端/浏览器直接调用的归 `4.1 前后端HTTP接口`；仅服务间调用的归 `4.2 后端RPC接口`；无法判断时按 `4.1` 处理并在文档中标注「待确认归类」。

### Vue 组件规则

一个 `.vue` 文件就是一个组件。在 `2.2 页面详情` 中：
- 只按 `.vue` 文件统计组件
- 每个页面下增加 `**组件拆分**`
- 表格列固定为：`模块 | 组件文件 | 作用 | 修改类型`
- 修改类型仅使用：`新增`、`修改`、`复用`

## 内容深度

这是概要设计，不是详细设计。

- 通过固定目录约束内容边界
- 通过表格/流程图/概览式描述输出
- 不主动下钻到 DDL、完整伪代码、字段级实现、异常分支穷举
- 读到更细材料，也只抽取对概要设计必要的信息

## 各章节规则

### 1.1 重点流程
- 用 PlantUML **时序图** 表达重点功能流程，不要把所有流程揉成一张总图
- 每张图聚焦一个需要多模块协作的重点功能
- 不需要把所有异常分支写全，但要把主要参与方与调用顺序表达清楚
- PlantUML 以「可渲染优先」而非「表达炫技优先」；默认使用简单、短句写法
- 参与者显示名一律加引号并使用 alias，例如 `actor "用户" as User`
- 时序图行为必须写成 `A -> B: ...` 或 `A -> A: ...`，禁止 `FE: ...` 这类无箭头写法
- 单条消息过长时用 `\n` 主动换行
- `alt / else / end` 必须成对出现；输出前逐张自检关键字拼写

### 1.2 状态机
- 用 PlantUML state diagram 表达状态流转
- 只保留关键状态与关键转移条件

### 2.1 页面变更
- 表格列固定：`模块 | 修改类型 | 页面名称 | path`
- 页面按模块归类和排序
- 修改类型仅使用：`新增`、`修改`、`-`

### 2.2 页面详情
- 页面按 `2.2.1` 起顺序展开
- 每个页面下先写标题，再写 `**组件拆分**`
- 组件说明聚焦「它是什么、负责什么」

### 3.1 ER图
- 从 DDL、模型定义、设计文档中抽取 ER 图
- package 名取数据库名
- 表使用实体表示，实体上只列有变更（`新增`、`修改`）的字段
- 优先表达主关系、外键关系、主业务关联关系

### 3.2 模块变更详细说明
- 表格列固定：`模块 | 变更类型 | 变更内容`
- 只写模块级增改，不写实现细节

### 3.3 接口概览
- 表格列固定：`模块 | 分类 | 接口名 | path | 变更类型`
- 必须同时覆盖：`前后端HTTP接口`、`后端RPC接口`、`后端MQ异步消息`
- MQ 行中的 `模块` 列写消息生产者的模块名；MQ 行的 `path` 列写 `Topic / Tag` 形式（如 `demo_ticket / ticket_approved`）
- 表格按 `模块`、`分类` 顺序排序
- 变更类型仅使用：`新增`、`修改`、`-`

### 4.1 前后端HTTP接口
- 来源优先使用 API 平台、接口清单、已有接口文档
- 若用户提供 API 平台 URL 或接口清单，优先调用 API 平台 MCP 工具
- 每个接口按 `4.1.1` 起编号
- 输出字段包括：模块、METHOD、PATH、API 平台链接（如有）；METHOD 可带 body 类型，如 `POST (json)`、`GET`
- 入参/返回值表格都加 `变更类型` 列
- 分类内部接口按 `模块`、`接口名` 排序

### 4.2 后端RPC接口
- 仅收录 `/<模块名>/api/` 前缀接口
- 编号从 `4.2.1` 起，输出风格与 `4.1` 一致
- 分类内部接口按 `模块`、`接口名` 排序

### 4.3 后端MQ异步消息
- 每条消息按 `4.3.1` 起编号，逐条用 `**黑体标签** + 内容` 写：`Topic`、`Tag`、`生产者`、`消费者`、`消息体`
- 不写消费逻辑（消费逻辑属于详细设计）
- 概要层级消息体只写包含哪些关键字段即可，不强制贴完整 struct

## API 平台使用

存在以下情况时优先使用 API 平台 MCP 工具：
- 用户提供了 API 平台 URL
- 用户提供了 API 平台接口清单
- 代码中接口定义不完整，但需要补接口文档

使用原则：所有 API 平台访问通过对应的 API 平台 MCP 工具（不同环境工具名可能不同，按实际可用工具调用）；先根据 URL / projectId / apiId 精确获取接口详情；不要凭经验猜接口字段（猜出来的字段会误导后续详细设计与开发）；token 或权限有问题时明确标注缺失，不要伪造内容。

## 默认输出设置

- 默认语言：中文
- 默认输出文件：`design-outline.md`
- 默认输出位置：需求规格文档所在目录
- 若用户明确指定路径，则以用户指定为准

## 标准流程

1. 先用 `AskUserQuestion` **必问**输入材料与输出方式
2. 读取需求规格文档、需求原始材料、设计材料、代码仓库
3. 判断是否存在页面归属歧义；若有，再用第二个 `AskUserQuestion` 确认前端页面归属
4. 判断是否存在后端表结构/领域归属歧义；若有，再用第三个 `AskUserQuestion` 确认后端归属
5. 如有必要查询 API 平台
6. 先搭出固定章节骨架
7. 按章节填充概要内容
8. 对不适用章节写 `无`
9. 输出为 markdown 文档

## 常见错误

- 把概要设计写成详细设计
- 没有先问输入材料和输出方式
- 混淆 `mis/public/api` 接口分类
- 在 `2.2` 中把非 `.vue` 文件也当组件
- 某章节不适用时留空，而不是写 `无`
- 没有使用 API 平台就直接猜接口结构
- PlantUML 参与者未加引号、消息未写箭头、`alt / else / end` 拼写错误导致语法报错
- PlantUML 消息文案过长不换行，导致图中文字拥挤
- 用户本地若报 `~1` / `HUFFMAN` / `bad URL`，优先判断为插件编码问题，不要误判为图语法问题
