# detailed-design

## 概述

基于《概要设计》(`design-outline.md`) 或《需求规格文档》(`requirement-spec.md`)，产出一份前后端《详细设计文档》`design-detail.md`。

- **后端**：Go 多模块，逐模块写领域层/接口/入口程序的详细设计
- **前端**：Vue，逐页面/组件写详细设计
- **真实性校验贯穿全程**：所有「已存在」实体必须经代码确认，禁止凭推测写入

## 输入与输出

- **输入**：`design-outline.md`（优先）/ `requirement-spec.md` / 代码仓库
- **输出**：`design-detail.md`（与输入文档同目录）

## 生成方式

详细设计分两次生成，降低返工：

1. **第一次生成**：先写**后端骨架 + ER 图 + 跨模块链路**，用 AskUserQuestion 确认
2. **第二次生成**：确认无问题后，再补全**各模块逐接口详细设计**与**前端组件详细设计**

## 真实性校验（贯穿全流程）

写入设计文档的所有「已存在」实体，必须通过代码确认真实存在，禁止靠推测/常识写入。

| 类型 | 校验方式 |
|------|----------|
| 已存在的 MySQL 表 | 到对应模块的 `models/` 目录里找到表定义 |
| 已存在的 HTTP 接口 path | 到对应模块的路由注册代码（router、controllers 注册处）确认 |
| 已存在的 MQ Topic / Tag | 到生产者代码中找到发送处确认 |
| 已存在的下游服务接口 | 到调用方代码或下游服务的路由代码中确认 |
| 已存在的 Redis key 前缀、定时任务名等 | 到对应代码确认 |
| 已存在的 Vue 组件/页面路由 | 到前端模块的 `.vue` 文件与路由配置确认 |

确认不到时，必须用 AskUserQuestion 向用户确认；不允许写一个「看起来合理但代码里不存在」的名字。

## 流程

### Step 1：浏览需求与代码
- 读取 `design-outline.md` / `requirement-spec.md`
- 浏览相关后端模块代码（models、controllers、service）与前端模块代码（页面、组件、接口封装），了解现有结构、调用方式、依赖关系

### Step 2：规划 ER 图
- 按领域列出每个模块新增/修改哪些表
- 新表名用中文，表变更写表名 + 要改的字段
- 修改表必须经《真实性校验》确认表名真实存在
- 用 AskUserQuestion 确认 ER 图无问题再继续

### Step 3：规划骨架并自查
- 规划跨模块链路（重点流程图）、模块间数据约定（MQ）、各模块入口程序、前端页面与组件清单
- 自查是否存在矛盾或不一致；不确定处用 AskUserQuestion 询问

### Step 4：先写入后端骨架
- 新建 `design-detail.md`，先写入「概要 + ER + 跨模块链路 + 模块间数据约定 + 各模块入口程序」
- 用 AskUserQuestion 确认无问题再继续

### Step 5：逐模块完成后端详细设计
- 数据最上游模块（MQ 生产者、被调用的 HTTP 接口）排在最上面
- 逐个模块写入详细设计

### Step 6：完成前端详细设计
- 逐页面、逐组件写入前端详细设计（见《前端详细设计》章节）

### Step 7：全量复核
检查整个文档自身是否矛盾，典型清单：
- 概要部分提到的接口/Topic 在详细设计里是否都有对应条目，反之亦然
- 所有已存在的表名、接口 path、Topic/Tag、Vue 组件都已通过《真实性校验》
- 所有 MQ 消息体只在「模块间数据约定」出现一次，其它位置只引用 `topic/tag`
- 模块排列顺序符合「数据最上游在最上面」
- 依赖项里引用的下游接口在被调用方详细设计里能找到对应入口
- 前端组件调用的接口在后端详细设计里都有定义
- 入口验证 case 都满足「给定输入，返回什么」的形式

## design-detail.md 文档结构

### 标题层级规则

| 内容 | 标题级别 | 示例 |
|------|---------|------|
| 文档标题 | `#` | `# 工单管理 - 详细设计文档` |
| 顶层章节 | `#` | `# 一、概要` / `# 二、后端详细设计` / `# 三、前端详细设计` |
| 概要主小节 / 模块标题 | `##` | `## 1. 领域 ER 图` / `## 1. demo-service` |
| 模块内主分节 | `###` | `### 1.1 模块级澄清` / `### 1.2 领域层变更` / `### 1.3 HTTP 接口` / `### 1.4 其它入口程序` |
| 模块内次分节 | `####` | `#### 1.1.1 依赖项` / `#### 1.2.1 数据结构` / `#### 1.3.1 提交工单` |
| 数据结构/command/刷数等细分 | `#####` | `##### 1.2.1.1 MySQL 表变更` |
| 固定说明项 | **不用标题，用黑体标签** | `**PATH**` / `**METHOD**` / `**入参**` / `**返回值**` / `**变更复杂度**` / `**逻辑概述**` / `**入口验证case**` |

完整层级示例、接口示例、MQ 示例、前端组件示例统一参考同目录 `examples.md`，不要在本 SKILL.md 内放长 demo。

# 一、概要

## 1. 领域 ER 图
- 只包含有新增/变更表的领域，不同领域用 package 分隔
- 新表名用中文不写字段；表变更写表名和要改的字段
- 表间关系标注 1:1、1:N 等
- 无变更的领域不写入

## 2. 重点流程（跨模块链路）
- 只关注模块间调用链路或 MQ，模块内详细逻辑不写
- 每个流程一个 PlantUML 序列图，participant 用模块简称
- 调用新接口写接口中文名不写 path；调用已存在接口（经《真实性校验》）写完整 path
- 禁止同一 participant 出现两个不同别名

## 3. 模块间数据约定（MQ 消息体变更）
每条新 MQ 必须在此处一次性定义清楚三件套，全文档其它位置只用 `topic/tag` 引用：
- **Topic** / **Tag** / **消息体**（Go struct，生产者消费者共用同一份）

## 4. 各模块入口程序
- 每个模块一个子表格，按模块排列
- 每行一个入口程序，列：`# | 类型 | 接口/Topic | 用途 | 变更`
- 「接口/Topic」填法：新 HTTP 接口写中文名；已存在 HTTP 接口（修改）写完整 path（经《真实性校验》）；MQ 消费写 `topic/tag`
- 类型取值：`HTTP MIS`、`HTTP API`、`HTTP Public`、`HTTP`、`MQ消费`、`定时任务`、`一次性任务`
- **MQ 生产不是入口程序，绝对不要写入入口程序表**。MQ 是被某真实入口（HTTP/MQ消费/定时任务）发送出去的副作用：在该入口「变更」列写「发送 xxx/xxx 的 mq」，在逻辑概述中用 `topic/tag` 引用消息体

# 二、后端详细设计

> **编号空间**：本章每个模块在 `## 二.N` 下展开（N 为模块序号）。下文模板里的 `X` 一律代表「二.模块序号」，即 `X.1` 实际写作 `二.1.1`、`二.2.1` 等。
> **跨章节引用**：任何位置引用接口/章节都必须带顶层中文序号，例如「见 §二.1.3.1」，禁止只写「§1.3.1」造成与前端章节同号混淆。

#### 模块排列顺序
数据最上游模块（MQ 生产者、HTTP 被调用者）在最上面，下游消费模块依次排列。

#### 每个模块固定四部分

##### X.1 模块级澄清 → X.1.1 依赖项
- 表格列出所有下游依赖，每个依赖明确到接口 path（如 `/demo/api/ticket/status`），不要写模糊描述
- 包括：HTTP 接口、Redis 锁、MQ、定时任务等

##### X.2 领域层变更 → X.2.1 数据结构
- MySQL 表结构变更：放完整 CREATE TABLE（新表）或 ALTER TABLE（表变更）
- MQ 相关：仅用 `topic/tag` 引用「模块间数据约定」，禁止重复贴消息体
- JSON 结构体：Go struct 定义，标注字段用途和约束

##### X.2.2 领域提供的 Command（如有领域层）
- 每个 command 单独成节：`X.2.2.N AggregateName.CommandName`
- 内部用黑体标签：`**Run 方法签名**`、`**结构体信息**`、`**调用方**`、`**变更复杂度**`、`**逻辑概述**`、`**验证 case**`
- `调用方` 用两列表格：`业务场景`、`调用方`

##### X.3 HTTP 接口
- **新增接口**：完整格式（入参、返回值、字段说明完整）
- **修改接口**：入参→「入参变更」、返回值→「返回值变更」；字段表列全所有字段（含未变更），加「变更类型」列，取值 `新增 / 修改 / 删除 / -`
- 现有字段必须到 controller / request struct / response struct 代码读真实定义，禁止凭印象写

##### X.4 其它入口程序
- 包含：MQ 消费、定时任务、一次性任务（MQ 生产不在此列）
- MQ 消费仅用 `topic/tag` 引用消息体
- 每个入口：标题、逻辑概述、入口验证case（规则同 §X.3）

### 变更复杂度规则（写在「逻辑概述」之前，独立一项）

**节点定义**：本期涉及的以下五类，每个算 1 个节点。节点是**业务语义级步骤**，不是物理 if 行数。**入参校验不算节点**：

| 内容类型 | 含义 |
|---------|------|
| 逻辑分支 | 业务语义上的判断分支或独立业务步骤 |
| 数据事务 | 单个数据库事务内的写操作（事务内多表写算 1 个节点） |
| io-mysql | MySQL 查询；或不在事务内的独立单表写 |
| io-接口 | 调用下游模块的 HTTP/RPC 接口（每个下游 path 算 1 个） |
| io-生产mq | 发送 MQ（每条 topic/tag 算 1 个） |

**分级判定**（先判强制高，否则按节点数）：

| 等级 | 节点数 |
|------|--------|
| 低 | ≤ 3 |
| 中 | 4 ~ 6 |
| 高 | > 6 |

**强制高条件**（存在即判高）：请求的下游接口存在幂等字段（如 `reqNo`、`requestId`、`idempotencyKey` 等）。

**书写要求**（所有等级一律用表格列节点，不写「略」、不写 bullet 列表）：

| 等级 | 是否画 UML | 节点表格 |
|------|-----------|---------|
| 低 | 否 | 必须列；即使 1 行也写表格 |
| 中 | 否 | 必须列全部节点 |
| 高 | 是（PlantUML 在表格前） | 必须列全部节点，与 UML 一致 |

**节点表格固定格式**：`# | 修改类型 | 内容类型 | 概述`，修改类型取 `新增/修改/删除/-`，内容类型取上文五类。

### 逻辑概述规则
- 先写「变更复杂度」，再写「逻辑概述」，所有等级用节点表格
- 入参校验不算节点；有 DB 写的写明涉及哪些表、写操作类型、幂等保障（分布式锁 key+TTL、唯一键名）
- 引用 MQ 用 `topic/tag`，MQ 生产节点内容类型固定 `io-生产mq`
- 触发「强制高」的节点在「概述」末尾括号点明原因

### 读接口字段依赖核对（强制）
- 读接口的「返回值」表必须加「数据来源」列，逐字段标注：本地表名 / 本地枚举 / 下游模块接口（用 ★ 标记）
- 标 ★ 的字段必须在「逻辑概述」中体现一条 `io-接口` 节点
- 返回值表后加结论：若不调用任何下游模块接口，明确写「**不调用任何下游模块接口**」

### 入口验证case规则
分两种情况：
- **需求文档有准入 case**：以准入 case 为源头，按责任边界拆分到各接口/入口，只保留当前接口真正负责且可观察的部分，不机械拆条凑数
- **没有准入 case**：根据「逻辑概述」生成，提炼输入条件、可观察返回、核心业务语义

**核心判断标准**：如果一句话不能落成「给定输入，接口返回什么」，通常不是好的接口层验收标准。

适合写：参数校验失败返回什么、业务条件满足/不满足返回什么、列表/详情核心业务字段语义、空数据返回。
禁止写：底层持久化细节（DB 落库成功）、不可观察的负向副作用、归类错误的 case、非本接口可验证的 case、纯集成测试场景（并发、分布式锁、MQ 时序）。

推荐句式：
- `WHEN 请求参数合法 THEN 系统 SHALL 返回成功响应`
- `IF 任一业务条件不满足 THEN 系统 SHALL 返回 canCreate=0 并给出具体原因`
- `WHEN 无匹配数据 THEN 系统 SHALL 返回 total=0 且 list=[]`

# 三、前端详细设计

> **编号空间**：本章每个页面在 `## 三.N` 下展开（N 为页面序号）。下文模板里的 `Y` 一律代表「三.页面序号」，即 `Y.1` 实际写作 `三.1.1`、`三.2.1` 等，与后端章节（二.*）不会同号。

前端按「页面 → 组件」逐层展开。1 个 `.vue` 文件就是 1 个组件。

#### 每个页面固定结构

##### Y.1 页面概述
- 路由 path、页面用途、入口来源、对应需求点
- 已存在路由必须经《真实性校验》确认

##### Y.2 组件树
- 用层级列表或表格表达页面下的组件父子关系
- 表格列：`组件文件 | 父组件 | 作用 | 修改类型`，修改类型取 `新增 / 修改 / 复用`

##### Y.3 组件详细设计（逐组件）
每个组件用黑体标签描述，不再加 markdown 标题层级：
- `**Props**`：输入属性，表格列 `名称 | 类型 | 必填 | 说明`
- `**Emits/事件**`：对外抛出的事件，表格列 `事件名 | 载荷 | 触发时机`
- `**本地状态**`：组件内部关键响应式状态（data/ref/reactive），只列影响交互的关键状态
- `**接口调用**`：调用的后端接口，表格列 `接口 path | 后端章节 | 触发时机 | 关键入参 | 用到的返回字段`；接口 path 必须与后端 HTTP 接口一致，并在「后端章节」列填可反查的引用（如 `§二.1.3.1`）
- `**交互逻辑**`：用节点表格或短句描述关键交互（提交、校验、状态切换、错误处理、空态/loading）
- `**前端验收点**`：可观察的 UI 行为，写成「给定操作，界面表现什么」

#### 前端验收点规则
- 写**用户可观察的界面行为**，不写组件内部实现细节
- 适合写：提交成功后页面变化、校验失败的错误提示文案、按钮置灰/隐藏条件、空态/loading 表现、列表筛选结果
- 条件触发的 toast/弹窗，文案要与 `requirement-spec.md` 一致
- 不写：某个内部方法是否被调用、某个 ref 的中间值

推荐句式：
- `WHEN 用户点击提交且必填项缺失 THEN 页面 SHALL 高亮缺失项并提示「请填写完整」`
- `WHILE 列表请求进行中 THEN 页面 SHALL 展示 loading 占位`
- `WHEN 接口返回空列表 THEN 页面 SHALL 展示统一空态文案`

## 全局规范

### 路径与表名书写规范
- **概要阶段**：新接口/新表的 path/表名未定，统一只写中文名
- **详细阶段**：path 和表名已在 §X.1 / §X.3 明确定义，全部写完整 path（接口）或完整表名（表）
- **已存在接口和表**（经《真实性校验》）：任何位置都写完整 path / 表名
- 新 path 命名：统一 `/<模块名>/子路径`，如 `/demo/mis/ticket/create`、`/demo/api/ticket/status`

### 禁止项

下列约束都是为了让详细设计能被开发「照着写」而不产生歧义、重复或二义引用，请遵守：

- 禁止在「各模块入口程序」中列出无变更的接口
- 禁止在入口程序列表中写入 MQ 生产行
- 禁止写「同 X.X.X」「参见 X.X.X」的引用，即使内容相同也要完整复制
- 禁止用 `{...}` 省略入参/返回值字段
- 禁止在 ER 图中写入无变更的领域
- 禁止重复放 MQ 消息体定义；统一在「模块间数据约定」集中展示
- 禁止虚构表名、接口 path、Topic/Tag、Vue 组件等已存在实体

## 常见错误
- 没做《真实性校验》就写「已存在」实体
- 前端组件调用的接口在后端详细设计里找不到对应定义
- 把「变更复杂度」写成 if 行数而不是业务语义节点
- 入口验证 case 写成无法观察的实现细节
- 前端验收点写成内部方法调用而不是界面可观察行为
- MQ 消息体重复定义
