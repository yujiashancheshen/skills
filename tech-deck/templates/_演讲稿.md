# 演讲稿规范（可选产出）

演示解决"观众看到什么"，演讲稿解决"演讲者怎么讲"。这是**可选**产出——只有用户要，才生成。

---

## 一、确认过程（两道确认，不臆断）

演讲稿风格因人而异，生成前必须确认，别默认按自己的偏好写。

**第一道确认 · 要不要（在步骤 0 诊断问答里一并问）**
把"是否需要配套演讲稿"作为诊断问答的一项。用户不要就跳过整个流程。

**第二道确认 · 怎么写（幻灯片交付后、写稿前）**
确认要之后，在动笔前再确认三件事，能推断的写明"我按 X 来，对吗"：

1. **风格**：精简提词（只给要点和关键句）/ 完整逐字稿（能直接照念）/ 技术深讲（多细节、多术语）/ 轻松口语（多类比、少术语）。
2. **时长**：几分钟的分享？据此定每页讲解详略（时长 ÷ 页数 ≈ 每页秒数）。
3. **是否含 Q&A 预案**：要不要预判听众提问并准备答法。

确认后才写。**绝不在未确认风格/时长时直接写整篇。**

---

## 二、结构规范

- **逐页对应**：每页幻灯片对应一段讲解，段首标注 `## 第 X 页 · 标题`，方便演讲时对照翻页。
- **每段三件事**：① 一句引导（把观众注意力带到这页）→ ② 核心讲解（把这页的 take-away 讲透）→ ③ 一句过渡（自然带到下一页）。
- **开头有总述**：封面页给一段"今天讲什么、分几块、为什么值得听"。
- **结尾有收束**：总结页把全篇串成一句话主线，收在价值上，别硬加互动问句。
- **信息量大的页加提示**：如密集架构图，加 `[提示：顺着主干线走一遍，不要逐个框念]` 这类演讲动作提示。
- **附 Q&A 预案**（若确认需要）：列 3-6 个最可能被问的问题 + 简短答法。

---

## 三、口吻（跟着宣讲对象走）

与幻灯片用的是同一个宣讲对象（步骤 0 已确认），口吻保持一致：

- 新人 / 跨团队：多铺垫、多打比方，术语先解释再用。
- 同行工程师：可直接用术语，重设计权衡与实现细节。
- 高管 / 决策层：结论先行，少过程，讲影响和取舍。
- 大会 / 激励：有节奏、有故事感、有记忆点。

---

## 四、内容铁律

1. **基于演示与原文，不编造**：讲解只能展开幻灯片和原始内容里已有的信息，不得杜撰数据、案例、结论。
2. **联网补充要标注**：若讲解里用到联网补来的信息，在稿中标明来源，与幻灯片口径一致。
3. **能对着念**：口语化短句，避免书面长从句；关键数字、信令号、术语照原文写准。
4. **不复述屏幕文字**：讲解是"把要点讲透、补上下文和为什么"，不是把幻灯片上的字再读一遍。

---

## 五、输出

- 输出为 Markdown 文件，文件名 `[主题]-演讲稿.md`。
- **与演示 HTML 同目录**（遵循 SKILL.md 步骤 4 的输出目录规则：输入来自文件就落在该文件同目录）。
- 顶部写清配套演示文件名、宣讲对象、建议时长，方便演讲者拿起就能用。
